\chapter*{Abstract}
\thispagestyle{plain}
Modern railway transportation reservation demands high database reliability, precise route sequencing, and strictly consistent seat accounting. This project presents the design and implementation of a full-stack, simplified IRCTC-style \textbf{Railway Reservation System} engineered specifically to demonstrate core relational database management principles. 

The application architecture combines a \textbf{PostgreSQL} relational database engine with a \textbf{Python Flask} web server, \textbf{Jinja2} server-rendered templates, and a responsive \textbf{Tailwind CSS} and vanilla JavaScript frontend. Rather than relying on commercial ORM abstractions, all database interactions execute direct, parameterized SQL statements via the \textbf{psycopg 3} driver to maintain complete SQL visibility and security against SQL injection. 

Key database features include:
\begin{enumerate}[label=(\roman*)]
    \item A formal conceptual \textbf{Entity-Relationship (ER)} model incorporating regular entities, existential-dependent weak entities (\texttt{train\_stops} and \texttt{booking\_passengers}), identifying relationships, and structural $(min, max)$ constraints.
    \item An explicit \textbf{7-step ER-to-relational conversion} adhering strictly to standard DBMS mapping algorithms.
    \item Complete functional dependency analysis ensuring that all relations achieve \textbf{Boyce-Codd Normal Form (BCNF)} without loss of functional dependencies.
    \item Concurrency-safe, atomic multi-passenger ticket reservation using PostgreSQL row-level locks (\texttt{SELECT ... FOR UPDATE}) to eliminate overbooking race conditions.
    \item A mandatory SQL View (\texttt{v\_train\_occupancy\_summary}) that encapsulates multi-table joins and real-time seat calculations for operations monitoring.
    \item An automated audit trail triggered by booking status updates (\texttt{trg\_booking\_cancellation}).
\end{enumerate}
The system was verified through an automated 12-test integration suite covering route ordering, multi-passenger booking atomicity, concurrency rollback, and passenger privacy protection during public PNR inquiries.

\chapter{Introduction and Motivation}

\section{Project Overview}
Railway reservation systems are among the most classic and mission-critical database applications. The Indian Railway Catering and Tourism Corporation (IRCTC) manages tens of millions of concurrent passenger transactions daily. While production enterprise systems incorporate distributed caching and microservice architectures, their fundamental data persistence and consistency guarantees rest upon relational database management systems (RDBMS) governed by ACID properties.

The goal of this project is to construct a simplified, self-contained, but functionally complete \textbf{Railway Reservation System (IRCTC Mini)} for a second-year B.Tech DBMS curriculum. The project avoids unnecessary frameworks, microservices, and ORM abstractions in favor of direct, transparent relational database design and raw parameterized SQL.

\section{Motivation}
In undergraduate database curricula, students often study relational algebra, normalization theory, and transaction isolation in isolation from actual web application development. Conversely, modern software tutorials frequently obscure relational foundations behind high-level Object-Relational Mappers (ORMs) such as SQLAlchemy or Hibernate, which hide SQL generation, locking mechanisms, and transaction boundaries.

The core motivation of this project is to bridge this gap:
\begin{itemize}
    \item To design a relational schema strictly from first principles using conceptual ER modeling.
    \item To systematically apply the theoretical 7-step mapping algorithm from ER constructs to relational tables.
    \item To demonstrate real-world normalization (verifying 1NF, 2NF, 3NF, and BCNF) to guarantee anomaly-free table designs.
    \item To demonstrate concurrency control by implementing pessimistic row-level locking to solve the ubiquitous ticket overbooking problem.
    \item To showcase advanced SQL constructs including correlated subqueries, multi-table joins, views, and event triggers.
\end{itemize}

\section{Problem Statement \& Scope Guardrails}
Designing an airline or railway ticketing database introduces complex domain requirements, such as route sequencing, berth quotas, and concurrent transactions. To maintain academic clarity, the following deliberate scope guardrails were established:
\begin{itemize}
    \item \textbf{Directional Route Validation:} An origin-to-destination search is valid if and only if the destination station occurs strictly after the source station along the ordered route stops.
    \item \textbf{Simplified Run Capacity:} Seats are reserved on a per-train-run, per-class capacity basis for the full run. Physical berth allocation (e.g., Upper, Middle, Lower), dynamic surge pricing, and segment-wise seat reuse are deliberately omitted.
    \item \textbf{Preservation of History:} Ticket cancellations do not delete database records; instead, booking status transitions to \texttt{CANCELLED}, restoring the class seat pool while maintaining an automated audit record.
\end{itemize}

\chapter{Conceptual Database Design (ER Modeling)}

\section{ER Modeling Conventions}
The conceptual model adheres strictly to the Chen ER notation taught in the reference curriculum (\textit{S\_ER Model.pptx}):
\begin{itemize}
    \item \textbf{Regular (Strong) Entities:} Rendered as single rectangles with primary key attributes underlined.
    \item \textbf{Weak Entities:} Rendered as double rectangles, exhibiting existential dependence on an owner entity, identified by an identifying relationship (double diamond) and a discriminator/partial key (dashed underline).
    \item \textbf{Attributes:} Rendered as ellipses attached to entities or relationships.
    \item \textbf{Structural Constraints:} Expressed using cardinality ratios ($1:1$, $1:N$, $M:N$) and participation constraints (single line for partial, double line for total), supplemented by precise $(min, max)$ constraints.
\end{itemize}

\section{Entity Sets Description}
\begin{enumerate}
    \item \textbf{USERS (Regular Entity):} Represents registered accounts. Attributes: $\underline{\text{user\_id}}$, $\text{email}$ [Unique], $\text{password\_hash}$, $\text{full\_name}$, $\text{phone}$, $\text{role}$ ($\in \{\text{'PASSENGER'}, \text{'ADMIN'}\}$), $\text{created\_at}$.
    \item \textbf{STATIONS (Regular Entity):} Represents railway junctions. Attributes: $\underline{\text{station\_code}}$, $\text{station\_name}$, $\text{city}$, $\text{state}$.
    \item \textbf{TRAINS (Regular Entity):} Master train entity. Attributes: $\underline{\text{train\_number}}$, $\text{train\_name}$, $\text{source\_station\_code}$, $\text{dest\_station\_code}$.
    \item \textbf{TRAIN\_STOPS (Weak Entity):} Existential-dependent on \texttt{TRAINS} via identifying relationship \texttt{HAS\_STOPS}. Partial key: \dashuline{\text{stop\_sequence}}. Attributes: $\text{arrival\_time}$, $\text{departure\_time}$, $\text{halt\_minutes}$, $\text{distance\_km}$.
    \item \textbf{TRAIN\_RUNS (Regular Entity):} Represents a scheduled train service on a specific calendar date. Attributes: $\underline{\text{run\_id}}$, $\text{journey\_date}$, $\text{status}$.
    \item \textbf{TRAVEL\_CLASSES (Regular Entity):} Travel classes. Attributes: $\underline{\text{class\_code}}$ (e.g., 'SL', '3AC', '2AC', '1AC'), $\text{class\_name}$.
    \item \textbf{BOOKINGS (Regular Entity):} Reservation transaction header. Attributes: $\underline{\text{booking\_id}}$, $\text{pnr}$ [Unique], $\text{booking\_date}$, $\text{total\_fare}$, $\text{booking\_status}$.
    \item \textbf{BOOKING\_PASSENGERS (Weak Entity):} Existential-dependent on \texttt{BOOKINGS} via identifying relationship \texttt{CONTAINS}. Partial key: \dashuline{\text{passenger\_seq}} ($1 \le \text{seq} \le 6$). Attributes: $\text{passenger\_name}$, $\text{age}$, $\text{gender}$.
\end{enumerate}

\chapter{Logical Database Design (ER-to-Relational Mapping)}

\section{The 7-Step Mapping Algorithm}
Following the 7-step mapping algorithm from the course references (\textit{Conversion of ERD to Relational Model\_1.pptx}):

\subsection*{Step 1: Mapping of Regular Entity Types}
For each regular entity $E$, create a relation $R$ containing all simple attributes. Select the entity key as primary key:
\begin{itemize}
    \item $\text{users}(\underline{\text{user\_id}}, \text{email}, \text{password\_hash}, \text{full\_name}, \text{phone}, \text{role}, \text{created\_at})$
    \item $\text{stations}(\underline{\text{station\_code}}, \text{station\_name}, \text{city}, \text{state})$
    \item $\text{travel\_classes}(\underline{\text{class\_code}}, \text{class\_name})$
\end{itemize}

\subsection*{Step 2: Mapping of Weak Entity Types}
For each weak entity $W$ with owner $E$, include the owner's primary key as a foreign key in $R$. The primary key of $R$ is the composite combination of the owner's primary key and the weak entity's partial key:
\begin{itemize}
    \item $\text{train\_stops}(\underline{\text{train\_number}, \text{stop\_sequence}}, \text{station\_code}, \text{arrival\_time}, \text{departure\_time}, \text{halt\_minutes}, \text{distance\_km})$\\
    Foreign key $\text{train\_number} \to \text{trains}(\text{train\_number})$ with \texttt{ON DELETE CASCADE}.
    \item $\text{booking\_passengers}(\underline{\text{booking\_id}, \text{passenger\_seq}}, \text{passenger\_name}, \text{age}, \text{gender})$\\
    Foreign key $\text{booking\_id} \to \text{bookings}(\text{booking\_id})$ with \texttt{ON DELETE CASCADE}.
\end{itemize}

\subsection*{Step 3: Mapping of Binary 1:1 Relationship Types}
Not present in this core model; relationships are naturally modeled as $1:N$.

\subsection*{Step 4: Mapping of Binary 1:N Relationship Types}
For each binary $1:N$ relationship from $T$ (1-side) to $S$ ($N$-side), include the primary key of $T$ as a foreign key in the relation representing $S$:
\begin{itemize}
    \item Relation $\text{trains}$: Includes foreign keys $\text{source\_station\_code}$ and $\text{destination\_station\_code}$ referencing $\text{stations}(\text{station\_code})$.
    \item Relation $\text{train\_runs}$: Includes foreign key $\text{train\_number} \to \text{trains}(\text{train\_number})$.
    \item Relation $\text{bookings}$: Includes foreign keys $\text{user\_id} \to \text{users}$, $\text{run\_id} \to \text{train\_runs}$, $\text{from\_station\_code} \to \text{stations}$, $\text{to\_station\_code} \to \text{stations}$, and $\text{class\_code} \to \text{travel\_classes}$.
\end{itemize}

\subsection*{Step 5: Mapping of Binary M:N Relationship Types}
For the $M:N$ relationship \texttt{OFFERS\_CLASS} between \texttt{TRAIN\_RUNS} and \texttt{TRAVEL\_CLASSES}, create a separate relationship relation whose primary key is the combination of the foreign keys of participating entities, plus relationship attributes:
\begin{itemize}
    \item $\text{train\_class\_capacity}(\underline{\text{run\_id}, \text{class\_code}}, \text{total\_capacity}, \text{base\_fare})$
\end{itemize}

\subsection*{Steps 6 \& 7: Multivalued Attributes and N-ary Relationships}
All attributes are designed atomically in 1NF; complex multi-entity associations are cleanly decomposed into binary relations.

\chapter{Normalization Analysis}

\section{Functional Dependencies (FDs) by Relation}
\begin{enumerate}
    \item \textbf{users:}
    \begin{itemize}
        \item $\text{user\_id} \to \text{email}, \text{password\_hash}, \text{full\_name}, \text{phone}, \text{role}, \text{created\_at}$
        \item $\text{email} \to \text{user\_id}, \text{password\_hash}, \text{full\_name}, \text{phone}, \text{role}, \text{created\_at}$
    \end{itemize}
    \item \textbf{stations:} $\text{station\_code} \to \text{station\_name}, \text{city}, \text{state}$
    \item \textbf{trains:} $\text{train\_number} \to \text{train\_name}, \text{source\_station\_code}, \text{destination\_station\_code}$
    \item \textbf{train\_stops:}
    \begin{itemize}
        \item $\{\text{train\_number}, \text{stop\_sequence}\} \to \text{station\_code}, \text{arrival\_time}, \text{departure\_time}, \text{halt\_minutes}, \text{distance\_km}$
        \item $\{\text{train\_number}, \text{station\_code}\} \to \text{stop\_sequence}, \text{arrival\_time}, \text{departure\_time}, \text{halt\_minutes}, \text{distance\_km}$
    \end{itemize}
    \item \textbf{train\_runs:}
    \begin{itemize}
        \item $\text{run\_id} \to \text{train\_number}, \text{journey\_date}, \text{status}$
        \item $\{\text{train\_number}, \text{journey\_date}\} \to \text{run\_id}, \text{status}$
    \end{itemize}
    \item \textbf{train\_class\_capacity:} $\{\text{run\_id}, \text{class\_code}\} \to \text{total\_capacity}, \text{base\_fare}$
    \item \textbf{bookings:}
    \begin{itemize}
        \item $\text{booking\_id} \to \text{pnr}, \text{user\_id}, \text{run\_id}, \text{from\_station\_code}, \text{to\_station\_code}, \text{class\_code}, \text{booking\_date}, \text{total\_fare}, \text{booking\_status}$
        \item $\text{pnr} \to \text{booking\_id}, \text{user\_id}, \text{run\_id}, \text{from\_station\_code}, \text{to\_station\_code}, \text{class\_code}, \text{booking\_date}, \text{total\_fare}, \text{booking\_status}$
    \end{itemize}
    \item \textbf{booking\_passengers:} $\{\text{booking\_id}, \text{passenger\_seq}\} \to \text{passenger\_name}, \text{age}, \text{gender}$
\end{enumerate}

\section{Verification of Normal Forms}
\begin{itemize}
    \item \textbf{1NF Verification:} All attributes hold atomic values from their respective underlying scalar domains. No multivalued lists or nested repeating groups exist.
    \item \textbf{2NF Verification:} A relation is in 2NF if it is in 1NF and no non-prime attribute is functionally dependent on a proper subset of any candidate key. In all composite-key relations (\texttt{train\_stops}, \texttt{train\_class\_capacity}, \texttt{booking\_passengers}), every non-prime attribute requires the full candidate key to be uniquely identified.
    \item \textbf{3NF Verification:} A relation is in 3NF if whenever $X \to Y$ holds, either $X$ is a superkey or $Y$ is a prime attribute. No non-prime attribute is transitively dependent on a primary key.
    \item \textbf{BCNF Verification:} A relation is in Boyce-Codd Normal Form (BCNF) if for every functional dependency $X \to Y$, $X$ is a superkey. In every relation defined above, every left-hand side determinant $X$ is a candidate key (or superkey). Therefore, all relations satisfy strict BCNF without requiring further decomposition.
\end{itemize}

\section{The Mandatory SQL View}
Per curriculum guidelines, the system defines \texttt{v\_train\_occupancy\_summary}. This view hides complex multi-table joins and aggregation logic from application queries:

\begin{lstlisting}[language=SQL, caption={Definition of Mandatory SQL View v\_train\_occupancy\_summary}]
CREATE VIEW v_train_occupancy_summary AS
SELECT
    tr.run_id,
    t.train_number,
    t.train_name,
    tr.journey_date,
    tr.status AS run_status,
    tc.class_code,
    cl.class_name,
    tc.total_capacity,
    tc.base_fare,
    COALESCE(COUNT(bp.passenger_seq), 0)::INT AS booked_seats,
    (tc.total_capacity - COALESCE(COUNT(bp.passenger_seq), 0))::INT AS available_seats
FROM train_runs tr
JOIN trains t ON tr.train_number = t.train_number
JOIN train_class_capacity tc ON tr.run_id = tc.run_id
JOIN travel_classes cl ON tc.class_code = cl.class_code
LEFT JOIN bookings b ON b.run_id = tr.run_id
    AND b.class_code = tc.class_code
    AND b.booking_status = 'CONFIRMED'
LEFT JOIN booking_passengers bp ON b.booking_id = bp.booking_id
GROUP BY
    tr.run_id, t.train_number, t.train_name,
    tr.journey_date, tr.status, tc.class_code,
    cl.class_name, tc.total_capacity, tc.base_fare;
\end{lstlisting}

\section{Automated Event Triggers}
To maintain a historical audit trail, a PostgreSQL trigger fires whenever a booking is cancelled:

\begin{lstlisting}[language=SQL, caption={Cancellation Audit Trigger and Function}]
CREATE OR REPLACE FUNCTION log_booking_cancellation()
RETURNS TRIGGER AS $$
BEGIN
    IF (OLD.booking_status = 'CONFIRMED' AND NEW.booking_status = 'CANCELLED') THEN
        INSERT INTO booking_cancellation_logs (booking_id, pnr, cancelled_at, cancellation_reason)
        VALUES (NEW.booking_id, NEW.pnr, CURRENT_TIMESTAMP, 'User requested cancellation');
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_booking_cancellation
AFTER UPDATE OF booking_status ON bookings
FOR EACH ROW
EXECUTE FUNCTION log_booking_cancellation();
\end{lstlisting}

\chapter{Transaction Management \& Concurrency Control}

\section{ACID Guarantees in Ticket Reservation}
A booking transaction must fulfill all four ACID properties:
\begin{itemize}
    \item \textbf{Atomicity:} The insertion of the \texttt{bookings} header and all associated \texttt{booking\_passengers} detail rows must either completely commit or completely roll back. A partial insertion (e.g., booking created without passengers) is never permitted.
    \item \textbf{Consistency:} Referential constraints, seat capacity limits, and passenger age limits must remain valid at all times.
    \item \textbf{Isolation:} Concurrent bookings must not read uncommitted capacity updates or double-allocate seats.
    \item \textbf{Durability:} Once committed, confirmed ticket reservations survive any system crash.
\end{itemize}

\section{Pessimistic Row-Level Locking (\texttt{SELECT ... FOR UPDATE})}
The classic \textit{overbooking race condition} occurs when two concurrent users query the remaining capacity of the last remaining seat simultaneously. Both threads read $\text{available} = 1$, proceed to insert booking records, and over-commit the train run.

To solve this concurrency anomaly without degrading overall database throughput, the system applies a pessimistic row-level lock on the specific \texttt{train\_class\_capacity} row:

\begin{lstlisting}[language=Python, caption={Atomic Concurrency-Safe Booking Transaction in app.py}]
with get_connection(autocommit=False) as conn:
    with conn.cursor() as cur:
        # 1. Lock the class capacity row exclusively for this run
        cur.execute("""
            SELECT total_capacity, base_fare 
            FROM train_class_capacity 
            WHERE run_id = %s AND class_code = %s 
            FOR UPDATE;
        """, (run_id, class_code))
        cap = cur.fetchone()
        
        # 2. Count active confirmed bookings under lock
        cur.execute("""
            SELECT COUNT(bp.passenger_seq) AS booked_count
            FROM bookings b
            JOIN booking_passengers bp ON b.booking_id = bp.booking_id
            WHERE b.run_id = %s AND b.class_code = %s AND b.booking_status = 'CONFIRMED';
        """, (run_id, class_code))
        booked = cur.fetchone()["booked_count"]
        
        # 3. Guardrail: Validate capacity
        if (cap["total_capacity"] - booked) < num_passengers:
            conn.rollback()
            flash("Insufficient seats remaining. Transaction rolled back.", "error")
            return redirect(url_for("index"))
            
        # 4. Insert booking & passenger records atomically
        cur.execute("INSERT INTO bookings (...) VALUES (...) RETURNING booking_id;", (...))
        booking_id = cur.fetchone()["booking_id"]
        
        for seq, name, age, gender in validated_passengers:
            cur.execute("INSERT INTO booking_passengers (...) VALUES (...);", (...))
            
    # Commit transaction
    conn.commit()

\chapter{Application Implementation}

\section{Backend Implementation}
The application logic is organized in two core Python modules:
\begin{itemize}
    \item \texttt{db.py}: Encapsulates database connectivity. It establishes native connections via \texttt{psycopg 3} with a 2-second timeout and dictionary row formatting (\texttt{dict\_row}). It also provides a transparent local development fallback adapter for offline testing.
    \item \texttt{app.py}: Implements HTTP request routes, input sanitization, Scrypt password hashing, session cookies, route direction logic, and transaction management.
\end{itemize}

\section{Frontend Implementation}
\begin{itemize}
    \item \textbf{Tailwind CSS Styling:} Utility classes are imported via CDN, configured with an IRCTC-inspired color palette (Deep Navy \texttt{\#0f1e36}, Sky Blue \texttt{\#0284c7}, and Slate \texttt{\#1e293b}).
    \item \textbf{Dynamic Passenger Management (\texttt{booking.js}):} Pure vanilla JavaScript dynamically appends and removes passenger rows in the DOM (enforcing a maximum of 6 passengers per booking) and continuously updates the live fare preview ($\text{Total Fare} = \text{Passenger Count} \times \text{Base Fare}$).
    \item \textbf{Printable E-Ticket (\texttt{print.css}):} Uses \texttt{@media print} CSS rules to hide interactive headers, footers, and buttons when printing, yielding an official Electronic Reservation Slip (ERS).
\end{itemize}

\chapter{Conclusion and Future Work}

\section{Conclusion}
This project successfully designed, modeled, and implemented an end-to-end Railway Reservation System aligned with academic DBMS principles. By eschewing heavy frameworks and ORM layers, the implementation delivers:
\begin{enumerate}
    \item A mathematically verified relational schema in Boyce-Codd Normal Form (BCNF).
    \item Practical mastery of the 7-step ER-to-relational mapping algorithm.
    \item Demonstrable SQL capabilities including multi-table joins, subqueries, views, and event triggers.
    \item Robust ACID transaction handling equipped with row-level locks to prevent overbooking anomalies.
\end{enumerate}

\section{Future Work}
Future enhancements to the system include:
\begin{itemize}
    \item \textbf{Segment-Wise Capacity Reuse:} Tracking station-to-station segment occupancy matrices to resell seats freed up midway along a route.
    \item \textbf{Automated Berth Allocation:} Implementing coach layouts (e.g., Sleeper, 3AC) and algorithmic seat allocation (Lower, Middle, Upper, Side Lower).
    \item \textbf{Waitlist and RAC Queues:} Managing FIFO waitlist priority queues that automatically promote passengers upon cancellation.
    \item \textbf{Production Cloud Deployment:} Packaging the service with Gunicorn for public deployment on platforms such as Render with managed PostgreSQL instances.
\end{itemize}
