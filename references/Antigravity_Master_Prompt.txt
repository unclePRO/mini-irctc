## 4. Website features (core requirements)
A. Users
- Register, log in and log out using securely hashed passwords and simple sessions.
- Require login to make bookings, view full booking history or cancel one's own bookings.

B. Train search and information
- Search trains by source station, destination station and journey date.
- Display train numbers/names, ordered intermediate stations, departure and arrival schedules, and journey duration.
- Support travel classes such as SL, 3AC and 2AC.
- Show date-wise, class-wise seat availability and fares.

C. Booking
- Book multiple passengers under a single booking and unique PNR.
- Validate passenger information and capacity in the backend.
- Save booking and passenger rows together in an atomic PostgreSQL transaction.
- Prevent overbooking even when two requests try to book the last places concurrently.
- Compute actual fare on the backend; JavaScript may only display a preview.

D. Manage bookings
- Enquire about limited PNR/booking status without exposing personal passenger data publicly.
- Show a logged-in user's booking history and full ticket details.
- Cancel an authorized booking; retain the record with CANCELLED status and restore capacity.
- Display a printable e-ticket using HTML and print-friendly CSS (no generated PDF necessary).

Optional after the core is working: a simple admin panel to manage trains/stations/routes and show booking, cancellation and fare summaries. Restrict admin access.

## 6. Explicit ER-to-relational conversion - follow conversion PPT
Show the mapping from the ER model to relational schemas BEFORE writing CREATE TABLE statements. Follow the seven ER-to-relational mapping steps taught in Conversion of ERD to Relational Model_1(1).pptx, whenever the corresponding construct occurs:

1. Regular entity: create a relation with its simple attributes and primary key.
2. Weak entity: create its relation, including the owner's key as a foreign key and the weak entity's partial key as appropriate.
3. Binary 1:1 relationship: use the appropriate foreign key approach, preferably on the total-participation side; consider the PPT's alternatives where justified.
4. Binary 1:N relationship: place the one-side's key as a foreign key on the many-side; account for relationship attributes.
5. Binary M:N relationship: create a separate relationship relation containing the participating keys and relationship attributes.
6. Multivalued attribute: create a separate relation containing the owner key and the attribute's value/components.
7. N-ary relationship: create a relationship relation with participating entity keys and relevant relationship attributes.

Only apply steps for constructs that actually exist in the ER diagram. Explicitly identify which mapping rule produced each resulting relation. Show primary keys, candidate keys, foreign keys, composite keys where needed and referential integrity. Make the final relational schema, ER diagram and actual SQL tables mutually consistent.

## 7. Normalization
For each relation, identify relevant functional dependencies and candidate keys. Verify 1NF, 2NF and 3NF, then aim for BCNF wherever feasible. If a relation stays in 3NF, provide a real, specific justification (such as preserving dependencies that BCNF decomposition would lose). Do not blindly claim that all relations are BCNF.

Aim for approximately 8-10 relations, but add or remove tables as demanded by correct modeling; do not sacrifice normalization to meet an arbitrary number.

Likely entities/relations to consider: Users, Stations, Trains, Train_Stops, Train_Runs, Travel_Classes, Train_Class_Capacity, Bookings and Booking_Passengers. Finalize them based on the actual ER model and functional dependencies.

## 8. SQL - follow SQL_Chapter_DB_1(2).pptx
This is the main DBMS implementation. Use appropriate SQL constructs from the professor's SQL chapter, not a complicated database abstraction.

MANDATORY - demonstrate with real schema/data and executable queries:
- DDL: CREATE TABLE and suitable PostgreSQL data types; show ALTER TABLE where meaningful.
- Constraints: PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK, DEFAULT, and suitable referential actions.
- DML: INSERT, SELECT, UPDATE, and DELETE where appropriate (do not delete booking history when cancelling).
- Queries: SELECT/FROM/WHERE, DISTINCT, ORDER BY, aliases, comparison and filtering.
- Joins: INNER JOIN and LEFT JOIN when relevant; join train/station/route/booking tables.
- Aggregates: COUNT, SUM, AVG, GROUP BY and HAVING with practical booking/occupancy examples.
- Subqueries: at least one useful nested subquery and one meaningful correlated subquery using EXISTS or NOT EXISTS, where appropriate.
- VIEW: create at least ONE real, meaningful SQL VIEW (for example, a train booking summary or confirmed-booking overview) and demonstrate querying it. Views are mandatory for this project.
- Transactions: booking and cancellation must be atomic; commit successful changes and roll back on failure. Use suitable row locking or an equivalent concurrency-safe design to prevent overbooking.
- Use direct SQL with psycopg placeholders/parameters, never construct SQL by concatenating user input.

OPTIONAL - only if they are simple and genuinely helpful:
- One window-function query, e.g. RANK() / ROW_NUMBER() for an optional train popularity or booking report. Window functions are NOT required for the core website and are not a main topic in the supplied SQL PPT.
- One small PostgreSQL trigger with an associated trigger function, e.g. a booking-cancellation audit, ONLY if it serves a real purpose and is easy to explain. The professor's PPT introduces triggers, but they are not essential to our app.
- Other small SQL features, such as an additional view or a simple index, if useful and understandable.

DO NOT implement merely to showcase syntax:
- CREATE ASSERTION (PostgreSQL does not implement SQL assertions).
- Complicated triggers, stored procedures/functions beyond an optional simple trigger function, heavy window-function logic or needless database-side automation.

Create:
  sql/schema.sql        - CREATE TABLE definitions, constraints, and the mandatory VIEW
  sql/seed.sql          - realistic fictional Indian railway data, repeatable or with clear reset instructions
  sql/demo_queries.sql  - clearly labeled executable examples of the SQL topics above, including JOINs, aggregates, GROUP BY/HAVING, nested/correlated subqueries and queries against the VIEW; optional window/trigger demos only if implemented

For any SQL feature not naturally called by a website page, it is fine to demonstrate it in sql/demo_queries.sql instead of artificially adding a new website feature. Keep optional scripts safe and clearly distinguish examples that modify data.

## 9. Simplified railway-booking assumptions
- Train defines a route; Train_Run denotes operation on a particular journey date.
- An origin/destination pair is valid only when the destination occurs AFTER the source among ordered train stops.
- Use per-train-run, per-class capacity. For simplicity, each confirmed passenger occupies one unit of capacity for the FULL train run even when travelling only part of the route. Describe this simplification in README.md.
- No physical seat numbers or berth allocation, overlapping segment reuse, waiting list, RAC, Tatkal, Premium Tatkal, VIKALP, dynamic fares, refunds, live train data or actual payments.
- Compute availability from capacity and confirmed passenger reservations.
- Protect capacity checks and inserts using a correct PostgreSQL transaction/lock strategy.
- Cancellation marks bookings as CANCELLED instead of deleting the booking.
